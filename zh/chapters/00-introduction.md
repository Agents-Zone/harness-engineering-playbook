# 引言：从 Vibe Coding 到 Harness Engineering

## 你遇到了墙

你大概已经用 Agent 写了一段时间代码了。

一开始体感很好。一个小功能，描述清楚，几分钟就出来了，比自己从零写快得多。你开始把越来越多的任务交给它，甚至开始想：也许我真的可以一个人干三个人的活。

然后你碰到了墙。

不是一下子碰到的，是慢慢感觉到的。项目大了，代码多了，你让 Agent 改一个功能，它改了，但把另一个功能搞坏了。你让它修那个 bug，它修了，又引入了新的 bug。你换了一个更强的模型，结果还是一样。你开始花大量时间检查它的产出，来回改四五轮，效率反而还不如自己写。

你开始怀疑：是 Agent 不够聪明？还是我用法有问题？

## 为什么 Demo 都很好看

回想一下那些让你觉得 Agent 很厉害的时刻，大部分是从零开始生成的东西。一个新项目、一个独立的脚本、一个 demo。从零开始的时候，Agent 确实很强。

但你的日常工作不是从零开始。你在一个已有的代码库上工作，要加新功能，要改需求，要修别人（或 Agent）之前写的 bug，要重构一段半年前的代码。这些工作有一个共同特点：演进。

Demo 之所以好看，因为它不需要演进。生成完就结束了，没有人会在 demo 上加第二个功能、改第三个需求。但演进才是软件工程的日常，一个项目 90% 的生命周期都在演进。Demo 掩盖了真正的难题。

## 为什么演进的时候会崩

Agent 有一些结构性的特征，让它在演进场景下的表现和你的直觉完全不同。

同样的 prompt，今天跑和明天跑，产出可能完全不一样。你觉得"上次这么说它就做对了"，但下次同样的话，它可能走一条完全不同的路径。从零生成的时候这不是什么问题，反正重来就好。但在已有的代码上做精确修改，这种非确定性就变成了灾难。

而且它没有持久记忆。每次对话都是一张白纸。上一轮你花了二十分钟给它讲清楚的架构决策、踩过的坑、约定的接口规范，全部归零。项目越大、历史越长，这个问题越致命。

更麻烦的是，它不知道自己错了。它会很自信地交付一个有 bug 的实现。如果你让它自己写测试来验证，它会写出一组刚好能通过自己代码的测试，自己出题自己答，当然全对。

这几个问题叠在一起，就是你碰到的那堵墙。项目小、迭代少的时候，你靠自己的判断力兜底，还能撑住。项目一大、迭代一多，你兜不住了，Agent 又不会自己兜，系统就开始崩。

你之前用的方法，写完看看对不对、不对再改，本质上是开环控制：给了输入，祈祷输出是对的。在确定性的世界里这没问题，但 Agent 不是确定性的。开环驱动一个非确定性的系统，失控只是时间问题。

## 你需要一套新的方法论

更好的 prompt 救不了你，更大的模型也救不了你。问题不在工具，在方法。

从开环到闭环，具体来说就是两件事。

第一件是规约。把你脑子里的意图变成 Agent 能精确执行的输入，不是"加一个搜索功能"这种模糊描述，而是一份机器可以对照执行的操作手册。你说得越清楚，Agent 理解错的概率越低，来回改的轮数越少。

第二件是验证。用自动化的手段证明产出是对的。不是你自己肉眼看，不是让 Agent 自己测自己，而是独立于 Agent 的、可重复的验证机制。而且验证不能等做完再查，得嵌在执行过程里，边做边反馈。

规约解决"做什么"，验证解决"做对没有"。这就是 harness engineering 的核心，给 Agent 装上缰绳，让它的能力可靠地发挥出来。

做到这两点，你的单次交互就能从碰运气变成工程化交付。这是本书第一卷要解决的问题。

## 稳定之后，闭环提效

规约和验证让你的产出稳定了。但你很快会发现新的瓶颈：你自己。

每个任务都需要你写 spec、盯过程、收结果。Agent 很快，但你一天能盯的任务有限，你成了整个系统的吞吐瓶颈。

下一步是让 Agent 自主执行。你给任务，它拆解、执行、自我检查，你回来收结果。再进一步，多个 Agent 并行工作，你从操作者变成指挥者。

这是本书第二卷的主题：从可靠到高效，从单次交互到规模化。

## 当个人效率不再是瓶颈

个人效率的问题解决了，瓶颈会转移到组织层面。团队的分工、流程、角色定义都是为人的速度设计的，跟不上 Agent 时代的节奏。

这是第三卷的主题。但在那之前，先从最紧迫的问题开始：怎么让 Agent 在你的项目上稳定地交付。
