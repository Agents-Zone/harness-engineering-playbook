# Harness Engineering 手册：章节 Outline（第二版）

> **原则：**
> - 每个阶段对应一章，章标题采用"概念——解释"的手册风格
> - 用户故事是章内小节的骨架，但不一定一一对应
> - 演进作为每卷的独立短章，三次性质不同
> - 小节内容留空待采访充实

---

## 引言：从 Vibe Coding 到 Harness Engineering

**这章要完成的事：**
- 用症状描述让读者确认"这本书是写给我的"
- 给出诊断：vibe coding 是开环的，harness engineering 是闭环的
- 给出全书地图（三卷结构），但不展开具体怎么做
- 引入 harness engineering 概念

**这章不做的事：**
- 不讲具体方法论
- 不讲 Agent 的技术原理（但会自然地渗透 Agent 的原理和结构性特征）

---

# 卷一：可靠的 Agent 编程（1.5x → 5-10x）

> **读者状态：** 用 Agent 写代码有一段时间了，知道 vibe coding 不够，读了引言理解了 harness engineering 的大方向。但具体到每天的工作，写的需求 Agent 总是理解不对，产出的代码也不知道怎么验证，整体效率大概 1.5x。
>
> **读完这一卷后能：** 写出 Agent 能准确执行的输入，建立可靠的验证闭环，掌握体系的基本维护方法，单次交互效率到 5-10x。

---

### 第一章：规约——把人脑里的意图变成机器能执行的输入

**这章要回答的核心问题：** 为什么 Agent 总是理解不对？怎么让它一次做对？

**章内用户故事线索：**
- 1.1 来回改 → 原来是我说不清楚
- 1.2 改了几轮发现方向就是错的 → 大方向要先对齐
- 1.3 做出来才发现漏了需求 → 需要系统检查需求完备性

**读者进入时的状态：** 理解了 harness engineering 的大方向，但不知道第一步该改什么。
**读者离开时的状态：** 能写出方向正确、需求完备的输入，Agent 单次产出基本靠谱。开始信任 Agent。

**小节：** 待采访确定

---

### 第二章：验证——从终端验收到过程质量控制

**这章要回答的核心问题：** Agent 产出的代码，到底该怎么验？

**章内用户故事线索：**
- 2.1 上线炸了才知道有 bug → 光有好输入不够，需要验证
- 2.2 让它自己写测试，自己出题自己答 → Agent 自测等于没测
- 2.3 看了也看不出来 → Agent 会偷懒，人肉 review 靠不住
- 2.4 等做完再查就晚了 → 验证要嵌进过程，不能放在最后

**读者进入时的状态：** 输入写好了，Agent 产出靠谱了，开始信任它了。然后出事了。
**读者离开时的状态：** 建立了从终端验收到过程质量控制的完整验证体系。单次交互效率到 5-10x。

**小节：** 待采访确定。因果链已经很清晰（出事→自测没用→人看也看不出→反馈太晚），可能直接按这条链组织小节。

### 第三章：演进——让规约和验证跟着代码活着

**这章要回答的核心问题：** 代码一直在变，怎么让 spec 和验证不烂掉？

**章内用户故事线索：**
- 卷一演进：spec 和验证过时了，我自己发现、自己改

**读者进入时的状态：** spec 和验证都建好了，跑了一两个月很稳。然后产品开始迭代，体系开始腐烂。
**读者离开时的状态：** 掌握了在 human-in-the-loop 模式下维护体系的方法。准备好进入下一阶段——放手。

**这次演进的性质：** 小张还在 human-in-the-loop 阶段，他自己能发现 spec 过时了，自己去改。本质是文档维护问题——怎么低成本保持 spec 和代码同步。

**小节：** ⚠️ 待采访充实。采访时注意区分 spec 腐烂（文档跟不上代码）和验证腐烂（测试跟不上需求变化）。

# 卷二：规模化 Agent 开发（5-10x → 几十倍）

> **读者状态：** 单次交互很高效了，spec 写得清楚，验证也闭环了，演进节奏也在摸索。但每个任务都需要实时在场，自己成了瓶颈。
>
> **读完这一卷后能：** 让 Agent 自主跑、多个 Agent 并行，从操作者变成分配者，个人产出突破 10x，并建立自动化的体系维护机制。

---

### 第四章：自主执行——上下文、分解与记忆

**这章要回答的核心问题：** Agent 的记忆到底是怎么回事？怎么让它在我不盯着的时候也不乱？

**章内用户故事线索：**
- 3.1 做着做着就乱了 → session 内的上下文限制，任务拆分和上下文控制
- 3.2 下次又是新实习生 → 跨 session 记忆归零，需要持久化机制

**读者进入时的状态：** 单次交互高效了，但自己成了瓶颈——每个任务都要在场。想放手。
**读者离开时的状态：** 能把任务交给 Agent 自主执行，自己去干别的事，回来收可用的结果。

**小节：** 待采访确定。两条故事（session 内 vs 跨 session）可能自然形成两大节。

---

### 第五章：多 Agent 并行——隔离与集成

**这章要回答的核心问题：** 多个 Agent 并行怎么不互相打架？怎么保证合得上？

**章内用户故事线索：**
- 4.1 互相覆盖 → 需要隔离机制
- 4.2 各自对但合起来炸 → 需要契约、集成和问题定位机制

**读者进入时的状态：** 单个 Agent 自主跑没问题了，想同时跑多个。
**读者离开时的状态：** 能同时指挥多个 Agent 并行工作，产出可靠地集成。个人产出接近几十倍。

**小节：** 待采访确定。两条故事（物理冲突→逻辑冲突）是自然递进。

> **注意：** 平台工程（静态分析、CI/CD、可观测性、Benchmark、IaC、排错能力）的内容融入本章，作为支撑多 Agent 并行的基础设施，而非独立成章。

### 第六章：演进——从人工巡检到自动化漂移检测

**这章要回答的核心问题：** 我不在场了，谁来发现 spec 和代码之间的漂移？

**章内用户故事线索：**
- 卷二演进：我不在场了，spec 烂了没人发现

**读者进入时的状态：** 多 Agent 并行跑起来了，自己不再实时盯着。然后发现 human-in-the-loop 的维护方式失效了。
**读者离开时的状态：** 建立了自动化的漂移检测机制，体系能在无人值守时自我监控。

**这次演进的性质：** 小张已经不在 loop 里了，human-in-the-loop 的维护方式失效。本质是监控和自愈问题——需要自动化机制检测体系与代码之间的漂移。

**小节：** ⚠️ 待采访充实。

## 采访指南

拿着这份 outline 去采访时，每章有两个核心问题要问：

**验证痛点：** "你有没有经历过[这章的用户故事]？当时具体是什么情况？"
→ 验证用户故事是否真实，收集具体场景作为章的开头素材

**收集解法：** "你是怎么解决的？试过哪些方法？哪些有效哪些没用？"
→ 填充小节内容，确定每章的内部结构

特别需要重点采访的章节：
- **第三章（卷一演进）：** 当前素材最薄，需要找到 human-in-the-loop 模式下维护 spec 的实践者
- **第六章（卷二演进）：** 需要找到在无人值守场景下做过自动化漂移检测的实践者
- **第七、八章（组织变革）：** 需要找到真正在团队层面推过 Agent 转型的 Tech Lead
