# 第一章 Outline：规约——与 Agent 对齐意图

> 状态：outline v4
> 日期：2026-04-07

## 全章 Takeaway

规约的本质是意图对齐。Agent 有限的注意力让意图对齐变成一个工程问题——你需要用结构化的方式传达意图，在被迫分解工作时控制每个边界上的漂移。

---

## 开篇：从 vibe coding 说起

**Takeaway：你跟 Agent 之间的核心问题不是"它不够聪明"，是意图没对齐。Vibe coding 的失败就是意图对齐失败的最日常体现。**

从 vibe coding 的体验切入。你跟 Agent 聊着天写代码，一开始挺顺，改着改着发现事情不对了。你说"把这个按钮改成蓝色"，它改了，但把你三轮前说的布局约束丢了。你说"别动那个模块"，它当时听了，二十轮之后又改了。你前面说"用 REST"，后面说"还是用 GraphQL 吧"，Agent 两个都看到了，但它不知道后面的覆盖前面的——对人来说后面的指令自然覆盖前面的，对 LLM 来说都是 context，没有先后权重。它可能试图调和两个矛盾的指令，也可能随机选一个，而你根本不知道它选了哪个。

这些不是 Agent 不聪明。这是你的意图活在对话里，而对话是一个会不断膨胀、自相矛盾、被稀释的载体。每多一轮对话，早期的意图就被压得更远。新开一个 session，所有意图归零。

诊断：vibe coding 的根本问题不是 prompt 写得不好，而是没有建立意图对齐的机制。Agent 可以在自己的理解里越做越好，但如果理解跟你的意图从来没对齐过，做得越好偏得越远。规约就是这个机制。

> 过渡：意图对齐听起来很简单——说清楚不就行了？但你会发现说清楚本身就是一个工程问题。

---

## 一、为什么意图对齐是一个工程问题

**Takeaway：因为 Agent 的注意力是有限资源。你不能把所有意图一次性灌给它，你被迫做信息架构的决策。**

理想情况下你只需要对齐一次——把项目的目标、架构、约束全告诉 Agent，它自己做对所有事。但 context window 有限，注意力不均匀（lost in the middle）。信息越多，每条分到的注意力越少。

所以你被迫做选择：什么信息、什么时候、以什么粒度给 Agent。这不再是"写好 prompt"的问题，而是信息架构的工程问题。

**案例：** Ryan 在单一上下文里处理多个功能点时，发现"相互之间的信息会出现干扰，导致混乱。虽然上下文窗口越来越大，但过多冗余信息下注意力还是不集中，然后漂移。"这个问题驱动了他后续所有的架构设计。

> 过渡：既然注意力有限，怎么用最少的信息、最清晰的结构完成对齐？

## 二、用结构传达意图

**Takeaway：结构化 spec + 持久化项目上下文，是在有限注意力下传达意图的两个基本手段。**

### 第一步：把意图从对话里拿出来

开篇说的 vibe coding 问题——意图活在对话里，越聊越丢——最直接的解法是把意图写成文档。文档可以原地修改（不会像对话那样累积矛盾），不随 session 消失，不跟对话内容争抢 context 空间。

这已经是一个巨大的进步。很多开发者从 vibe coding 切换到文档驱动后，立刻感觉到效果。但光写下来还不够。

### 为什么光写下来不够：结构消除歧义

来回改五轮常常不是 Agent 理解错了，是你自己没想清楚。"加一个搜索功能"——搜什么？怎么排序？空结果怎么办？你没想过这些问题，Agent 替你做了决定，做出来你一看不对。

结构化 spec 首先是逼你自己把模糊的想法具体化的工具。不是写更长的自然语言，而是用字段和格式让每个维度的意图显式表达。

**案例：** GitHub 的 Spec Kit 在 spec 模板里禁止写 HOW（技术栈、API、代码结构），只允许写 WHAT 和 WHY。这个约束的意义不在于规范 Agent，而在于防止人在没想清楚"做什么"之前就跳到"怎么做"。

### 结构比自然语言信息密度高

不是写更长的 prompt，而是用字段和格式让每个维度的意图显式表达。看过的主流框架——BMAD、OpenSpec、Spec Kit、AILock-Step——spec 模板差异很大，但都包含三个共同维度：

- **意图**：这个功能为谁解决什么问题（用户价值点 / 用户故事）
- **验收**：怎么算做对了（Given/When/Then / Gherkin 场景）
- **约束**：不该动什么（影响分析 / 已有模块 / 强制规则）

每个字段不是仪式，是防线。Ryan 发现当 spec 里技术架构相关的字段为空时，后续的 develop agent 会出现幻觉开始乱写——空的字段意味着那个维度的对齐没有发生。

### Agent 不知道你没说的事

意图不只是"这次做什么"，还有"在什么背景下做"。你脑子里的项目架构、已有模块、命名规范，Agent 一个字都不知道。

你需要一个持久化的项目上下文，跟任务级 spec 分开管理。项目上下文像一本索引书：Agent 不用背下全部代码，但知道去哪里找需要的东西。这解决了一个关键问题——Agent 发现已有 IPC 模块不用重写，但前提是项目上下文里记录了这个模块的存在。

项目上下文和行为规则是两回事。行为规则说"不许做什么"（CLAUDE.md），项目上下文说"可以用什么"（技术栈、目录结构、模块索引、代码模式）。前者是约束，后者是知识。

> 以用户价值描述的需求天然具有可验证性——"用户能注册吗？"有明确的 yes/no 答案。后面讲分解时会回到这一点。

> 过渡：结构化 spec + 项目上下文解决了小任务的对齐。但需求一大就不行了——上下文被淹没。

## 三、分解与漂移

**Takeaway：你被迫分解工作（因为 context 有限），但每次分解都制造意图漂移的风险。按可验证的单元分解、在关键边界上 re-align，是控制漂移的方法。**

### 大 feature 为什么崩

六七个功能点交织在一起的 spec 加上项目上下文加上代码，总量超过 Agent 能有效处理的范围。做到第三个功能点时，前两个的约束已经被冲掉。不是 Agent 不聪明，是上下文被淹没了。

你被迫分解。但分解不只是降低单次难度——每次分解都创造一个新的边界，每个边界都是意图可能偏移的地方。项目→feature 丢一层，feature→task 再丢一层，task→代码又丢一层。

### 按用户价值分解

分解的方式决定了你能不能在边界上验证意图。

按技术层拆——数据库一个任务、API 一个任务、前端一个任务——每个子任务做完你没法验证意图。"数据库表建了"，对不对？不知道，得等 API 和前端都做完才能判断。

按用户价值拆——"用户能注册"一个任务、"用户能登录"另一个——每个做完就能验证："一个用户能不能走完注册流程？"能就对了。

**案例：** AILock-Step 的拆分规则明确禁止按技术层拆分。正确的拆法：feat-auth-register（用户能注册，独立可交付）→ feat-auth-login（用户能登录，依赖注册）→ feat-auth-permission（用户管权限，依赖登录）。错误的拆法：feat-auth-db / feat-auth-api / feat-auth-ui——每个都没有独立用户价值，无法在边界上验证对齐。

当一个 feature 的用户价值点超过一定数量（比如 3 个），就是拆分的信号。每个子 feature 之间的依赖关系需要显式记录，执行按依赖顺序进行。

### 在关键边界上 re-align

分解之后，每个边界都是意图可能丢失的地方。好消息是，不是每个边界都需要同样的投入。越上层的检查成本越低、价值越高——一个 feature 方向错了，下面所有 task 白做。

一种有效的实践是让 Agent 对同一份需求做多次不同角度的思考：从需求出发生成实现方案（第一次理解），从方案拆成执行步骤（第二次理解，暴露漏洞），从步骤反推验收标准（第三次理解，从"怎么做"反推"怎么算对"）。三次产出之间的矛盾就是漂移的信号。

人在这个过程中的角色是在第一次产出后看一眼用户故事：Agent 理解的"这个功能为谁解决什么问题"跟你想的一样吗？一样就放手。Ryan 的经验是"一个 user story 几个不同的场景描述，就已经能判断出 AI 跟我的理解了。"这是整个流程中成本最低、价值最高的对齐检查点。

> **规约的重量：** 不是所有任务都需要完整的分解和结构化 spec。三句话能说清的需求走完整流程是浪费——Ryan 用 BMAD 框架做一个小优化花了一天，不如直接说一句话。规约的重量要匹配任务的风险和复杂度。而且规约本身也消耗 context——文档越多 Agent 越难聚焦。过度规约和规约不足殊途同归。实践中的平衡点：feature 层面敏捷迭代，feature 内部 spec 驱动。

> 过渡：原理讲完了，看看在真实项目里长什么样。

## 四、Case Study

**Takeaway：这些 principle 在真实项目中是一套连贯的工作流，不是零散的 best practice。**

以 Ryan 的 AILock-Step Feature Workflow 为例，展示一个需求从进入到交付的完整过程。这个系统经过 40+ feature 的实战验证。

Walkthrough：
1. 项目上下文 + 行为规则分工 → Agent 知道已有什么、不许做什么
2. 需求进入 → 分析用户价值点、生成验收场景、评估规模
3. 规模过大 → 按用户价值拆分，记录依赖关系
4. 三次思考 → spec → task → checklist 交叉校验
5. 人 review 用户故事确认方向
6. 隔离执行 → 独立 worktree，防止 context 交叉污染
