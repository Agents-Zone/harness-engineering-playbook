# 02C Outline：迭代出一份可执行的 Spec

> 状态：v5 outline
> 日期：2026-04-07

## Section Takeaway

Spec 不是一次写出来的，是迭代出来的。你写意图，Agent 展开，交叉验证暴露问题，你修正或拆分，再验证，直到收敛。在这个循环里，只有人能判断意图是否对齐，因为意图只存在于人脑子里。循环该跑多少轮、人该投入多少时间，取决于做错了返工的代价有多大。

主线：**一个迭代循环，从模糊需求到可以交给 Agent 执行的 spec。**

---

## 一、迭代循环

### 起点：写意图

**段落 1**
- Takeaway：一两句用户故事是迭代的种子，它定方向，不定细节
- 你拿到一个需求，第一件事是写用户故事："作为 X，我希望 Y，这样 Z。"写这句话逼你做三个决策：给谁用、干什么、为什么。写不出来说明你对需求理解不够，应该去澄清。
- 这不是 spec 的终稿，是迭代的起点。你不需要在这一步想清楚所有细节。

### 第一轮：Agent 展开

**段落 2**
- Takeaway：你提供方向，Agent 把它展开成覆盖三个维度的 spec 草稿
- 你把用户故事和大概的范围给 Agent，它生成 spec 草稿。在这个过程中 Agent 会做很多事：从项目上下文里找相关模块，推测可能的影响范围，生成验收场景（它可能想到你没考虑过的边界条件），建议技术方案。
- 案例：Ryan 的 /new-feature skill。Agent 加载 project context，分析用户价值点，生成 Gherkin 验收场景，评估规模。几分钟产出一份完整的 spec 草稿。
- 这份草稿大概率有问题。可能遗漏了一个你关心的边界情况，可能验收场景跟你的意图有偏差，可能影响分析漏了一个模块。这没关系，下一步会暴露这些问题。

### 交叉验证

**段落 3**
- Takeaway：让 Agent 从 spec 推 task，从 task 推 checklist。矛盾就是需要修正的信号。
- 02B 讲了交叉验证的原理。在实际操作中，这一步是让 Agent 从 spec 生成 task list（第二次理解需求），再从 task list 生成 checklist（第三次理解需求）。
- 你比较三份文档。checklist 里出现了 spec 没提到的检查项？spec 可能有遗漏。task 的某个步骤跟 spec 的意图矛盾？spec 在那个地方可能有歧义。三份文档一致？Agent 从三个角度看到了同一个东西。

### 修正

**段落 4**
- Takeaway：交叉验证暴露的问题指向 spec 的具体位置，你改那里，再跑一轮
- 交叉验证发现矛盾之后，你回到 spec 修正有问题的部分。可能是补一个遗漏的验收场景，可能是澄清一句有歧义的描述，可能是加一条被忽略的约束。改完之后让 Agent 重新生成 task list 和 checklist，看矛盾是否消除。
- 这个循环通常一两轮就收敛。每一轮的成本都很低，都是文档层面的操作。但它拦住的问题如果拖到代码阶段才发现，修正成本会高几个数量级。

### 分支：需求太大，拆分

**段落 5**
- Takeaway：迭代过程中发现 spec 收敛不了，往往是因为需求太大，这时候拆分是循环内的一个分支而不是一个独立阶段
- 有几个信号提示需求该拆了：用户价值点超过三个，验收场景超过七八个且场景之间有复杂依赖，影响模块超过四五个。
- 还有一个更直觉的信号：你跑了两三轮交叉验证，矛盾怎么也消不掉。每次修了一个问题又冒出来另一个。这通常说明 spec 里包含了多个独立的用户价值，它们之间的交互让 Agent 没法在一个 context 里同时处理好。

**段落 6**
- Takeaway：LLM 天然擅长分解自然语言需求，你提供拆分原则就行
- 你告诉 Agent 拆分的原则：按用户价值拆，每个子单元是一个用户可以独立验收的功能。Agent 来执行拆分。
- 案例：AILock-Step 的拆分。"用户认证系统"拆成 feat-auth-register（用户能注册）→ feat-auth-login（用户能登录，依赖注册）→ feat-auth-permission（用户管权限，依赖登录）。每个有独立的用户故事和验收场景。
- 按技术层拆（feat-auth-db / feat-auth-api / feat-auth-ui）做不到这一点：每个子任务没有独立的验收标准，交叉验证在那个粒度上无法运行。

**段落 7**
- Takeaway：拆完之后每个子 spec 进入同样的迭代循环
- 拆分产出若干个子 feature，每个有自己的 spec 草稿。这些草稿跟原始需求的意图一致吗？不知道。每个子 spec 进入同样的 write → cross-validate → refine 循环。
- 这里多了一层检查：子 spec 跟原始需求的对齐。如果原始需求说"认证系统需要支持 OAuth"，但拆出来的 feat-auth-login 只有用户名密码登录没有 OAuth，交叉验证会暴露这个遗漏（checklist 里会出现 spec 没覆盖的检查项）。

### 收敛

**段落 8**
- Takeaway：交叉验证不再产生矛盾，spec 可以进入执行
- 三份文档一致意味着 Agent 从三个角度看到了同一个东西。这不保证 spec 是完美的（你自己都没想到的边界情况不会出现在任何文档里），但它保证了 spec 内部自洽，Agent 的理解在多个角度上一致。
- 如果某个维度确实没有内容，显式写"无"。空着意味着没被思考过，"无"意味着思考过了。

## 二、人在循环中的角色

**段落 1：意图对齐只能由人来做**
- Takeaway：意图存在于人脑子里，Agent 从定义上无法检查它不知道的东西
- 交叉验证能检查文档之间的一致性：spec 说 A，task 说 A，checklist 说 A，一致。但它无法回答：A 是不是你真正想要的。
- 你写的用户故事说"用户能搜索文章"。Agent 展开了验收场景，交叉验证通过了，三份文档完全一致。但你脑子里想的搜索是只搜标题，Agent 理解的是全文搜索。这个偏差不会在任何自动化检查中被发现，因为 Agent 的三轮思考都基于同一个（跟你不同的）理解。
- 你是软件的最终使用者或使用者的代理人。只有你能判断"这是不是我想要的"。这个判断不能被委托。

**段落 2：人看什么**
- Takeaway：用户故事和关键验收场景，这两个对了其他的可以放手
- 你不需要 review 每一行 task，不需要逐条检查 checklist。你需要看的是：
  - 用户故事：描述的"谁""做什么""为什么"跟你脑子里一致吗？
  - 关键验收场景：主要路径对吗？你最关心的边界情况在里面吗？
- 上层方向对了，下层不太会出大问题。上层方向错了，下面全白做。所以你的时间应该花在上层。
- Ryan 的经验："一个 user story 加几个场景描述，就已经能判断出 AI 跟我的理解了。"

**段落 3：Agent 看什么**
- Takeaway：一致性检查是结构性工作，Agent 比人更适合
- Agent 擅长的检查：跨文档矛盾检测（spec 说按相关度排序，checklist 说按时间排序）、覆盖度检查（spec 有五个验收场景，task list 只覆盖三个）、术语一致性（spec 里叫"文章"，task 里叫"帖子"）、重复检测（两个子 feature 描述了同一个功能）。
- 这些检查不需要知道意图，只需要比较文档之间的结构是否一致。Agent 能同时处理所有文档的完整内容，不会因为文档多而遗漏。
- 整个迭代循环里的交叉验证就是 Agent 在做一致性检查。人在循环中的介入点是 Agent 无法覆盖的地方：意图对齐。

## 三、这个循环该跑多重

**段落 1：motivation**
- Takeaway：人的注意力是整个流程中最稀缺的资源，不是每个任务都值得人做深度 review
- Agent 做交叉验证和一致性检查几乎不花你的时间。但你 review 用户故事、判断意图是否一致、决定要不要改 spec，这些需要你的专注力。整个循环中 Agent 的部分可以自动化，人的部分不能。
- 问题变成：什么任务值得你投入这些专注力？

**段落 2：返工成本决定投入**
- Takeaway：做错了返工的代价有多大，就决定了你该在 spec 阶段花多少时间
- 改一个按钮文案，做错了重做一分钟。花十分钟 review spec 不划算。直接告诉 Agent 改什么，加一句约束（别动别的），让它自己跑交叉验证自检就够。
- 一个涉及三个模块的新 feature，做错了可能浪费一整天。值得花十分钟 review 用户故事和验收场景。
- 一个涉及五个以上模块的大需求，做错了可能浪费一周。先拆分，每个子 spec 都认真 review。
- 判断标准不是任务的代码量，而是做错了有多疼。一个只改两行但影响支付流程的任务，比改一百行管理后台的任务更值得在 spec 阶段投入时间。

**段落 3：整个循环的灵活性**
- Takeaway：同一个迭代循环可以跑得很轻也可以跑得很重，取决于你在哪些环节投入人的注意力
- 最轻的情况：你写一句意图加一条约束，Agent 自己展开和交叉验证，你不 review，直接执行。适合改文案、修样式这类低风险任务。
- 中等情况：你写意图，Agent 展开，你 review 用户故事和验收场景，交叉验证通过后执行。适合大部分新 feature。
- 最重的情况：你写意图，Agent 展开，你深度 review，拆分，每个子 spec 单独迭代，每个都 review。适合高风险、大范围的需求。
- 这不是三个不同的流程，是同一个循环在不同风险等级下的不同运行方式。循环本身不变，变的是人在哪些环节介入。
