# 第五章 Outline：验证

> 状态：detailed outline (v2)
> 日期：2026-07-10
> 依据：[docs/volume2-outline.md](volume2-outline.md)、[docs/ch4-outline.md](ch4-outline.md)

## 章级 takeaway

执行时人不再做最终裁判。验证机制必须自己产出可信结论。漂移只在两个地点发生。代码与载体块之间，载体块与载体块之间。可信度从这两个地点各自有专门机制、且机制之间的失效边界显式可陈述来。三层机制针对两个地点：硬门禁和软门禁针对代码与载体之间（按机制性质拆），集成验证针对载体块之间。建立机制沿用 4.3 的共同产出框架，元原则相同，只是判定内容从意图变成失效边界。

## 章的论证链

Ch4 问载体长什么样。Ch5 问验证凭什么可信。可信不是任何单机制的属性，来自机制之间的失效互补。互补分析要从"漂移可能在哪里发生"起手。漂移只有两个地点。这一步先把问题空间确定，再推出机制设计。三层机制是两个地点加机制性质的具体展开。最后用一个真实项目走完流程，同时展示机制怎么从载体建立起来和跑起来抓什么。

四节的角色：

- 5.1 建立议题。人退出裁判位置后，验证责任转移到机制
- 5.2 分析漂移空间。漂移只在两个地点发生，可信度来自两个地点的机制覆盖加失效边界显式
- 5.3 引入三层机制。代码与载体之间的漂移按机制性质拆两层，载体块之间独立一层
- 5.4 走完一遍流程。用 ch4 的博客审核队列，展示三层机制怎么从载体建立起来、跑起来抓到什么

## 5.1 验证从人转移到机制

### Section takeaway

卷一里验证的最后一道是人做裁判。卷二里两件事联合破坏了这个前提。带宽（人物理上盯不完）和盲区（人在陌生领域里判定不了）。验证责任必须从人转移到机制。

### 段落

**段 1：卷一验证的三层结构**

Takeaway：卷一的验证由测试、code review 和人组成。人在三层里是最后兜底。

测试查代码行为。Code review 查代码意图。前两者都会漏。漏的地方靠人对项目的理解补位。

这个结构里最关键的是人。测试和 review 可以自动化到某种程度，最后拿主意的是人。前两层可以做得相对宽松，因为最后一层能补位。

**段 2：卷二的带宽约束**

Takeaway：并行 Agent 的产出速度超过人的 review 速度。

卷一时一天可能 review 三四段代码，每段能过一遍眼。卷二时并行 Agent 一天可能产出几十段代码。人物理上看不完。看的速度追不上产出的速度。

带宽是硬约束。不看又装作看过等于放过，看不完等于漏检。

**段 3：卷二的盲区约束**

Takeaway：在陌生领域里人做不了裁判。

卷一时项目通常在熟悉的领域内，凭业务理解能判断代码对不对。换到陌生领域，判断力接近零。做后端的看 CV 算法代码，做产品的看数据库存储引擎设计，看得懂符号看不懂含义。

胥克谦的原话，说他做开发工具项目："里边百分之九十九都是盲区。"跨领域时判定率骤降不是特例，是任何一个人换行业都会遇到的物理现实。

**段 4：两个约束常同时出现**

Takeaway：规模够大的项目常常同时超出个人带宽和个人领域。

大规模项目往往覆盖多个专业面。你熟悉其中一两个，其他都是盲区。同时产出速度又超过你的 review 速度。两个约束不独立。它们相关，常同时起作用。

任意一个约束成立，卷一模式都失效。两个都成立时更加成立。

**段 5：验证责任转移到机制**

Takeaway：人退出裁判位置后，可信结论必须由机制自己产出。

这里要澄清一个方向。机制产出可信结论的方式，是在自己的能力边界内给出确定的判断，加上把边界外的部分交出去。这跟"机制模仿人的判断"是完全不同的两件事。前者可行，后者不可行。

机制自己怎么可信是下一节的核心问题。

### 与卷一的引用点

- 卷一 03 章验证三层结构：这里承接。三层里前两层保留，责任升级；第三层不再成立
- 卷一 03c 实践部分：不重复细节，只承接结论"三层配合工作"

### 写作陷阱

- 段 2、段 3 讲带宽和盲区不要写成对读者的评价。这是所有人在卷二规模下都会遇到的物理事实
- 段 3 引胥克谦的原话作例子，不作权威背书
- 段 5 不要展开机制设计。展开留给 5.2

## 5.2 漂移的两个地点

### Section takeaway

验证的可信来源需要先分析漂移空间。漂移只在两个地点发生。代码与载体块之间，载体块与载体块之间。每个地点要有专门机制。可信从两个地点的机制覆盖加机制间的失效边界显式来。

### 段落

**段 1：机制自己可信的问题**

Takeaway：机制要可信，前提是它承担的责任落在明确的范围里。

上一节推出验证责任要从人转移到机制。这一节问一个更具体的问题。机制承担什么责任才能可信。

答案的第一步是把机制要防的东西列清楚。机制防的东西是漂移。漂移是产出偏离意图的地方。要机制可信，先要知道漂移可能在哪里发生。漂移空间不清楚，机制承担的责任就模糊。责任模糊的机制不可信。

**段 2：漂移的第一个地点是代码与载体块之间**

Takeaway：Agent 从载体块产出代码，代码可能不忠实于载体块。

Agent 拿到一个载体块，产出代码。载体块规定了这一块的意图。代码是意图的实现。两者之间可能有偏离。

偏离的具体形态。代码的函数签名跟载体规定的契约不符。代码的 schema 字段类型跟载体规定的类型不符。代码的业务逻辑跟载体规定的语义不符。代码的错误处理跟载体规定的策略不符。

这些都属于代码没有忠实实现载体块。这是漂移的第一个地点。

**段 3：漂移的第二个地点是载体块之间**

Takeaway：载体的多个块之间可能不一致。不一致下产出的代码合不上。

ch4 建立的自足性推出载体块之间有冗余。一条决策被自足到多个块里。冗余的地方要保持一致。共同产出流程里的一致性检查会漏。

不一致的具体形态。前端块的 API 契约说 session 用 cookie 传，后端块的 API 契约说 session 用 header 传。schema 块规定 reviewer_id 是 uuid，产品交互块的 UI 状态图里 reviewer_id 类型隐含是整数。两个块的意图错位。基于错位的载体块产出的代码互相不匹配。

这是漂移的第二个地点。它跟第一个地点性质不同。第一个地点的漂在单块内可以判断。第二个地点的漂只有跨块看才能判断。

**段 4：两个地点覆盖所有漂移**

Takeaway：漂移只可能出现在这两个地点，其他地方漂不会传递到产出上。

意图形成阶段的漂在 ch4 里由共同产出机制处理。载体块生成阶段的漂也在 ch4 处理。到了 ch5，载体已经在手，漂只可能在两个地方。要么代码没对齐载体，要么载体块之间自己就漂了。

两个地点组成完整的漂移空间。机制要可信，必须在这两个地点都有覆盖。

**段 5：可信度从失效边界显式的机制组合涌现**

Takeaway：机制的可信不来自机制自己"聪明"。来自两个地点各有机制，且每个机制的失效边界能陈述。

每个机制都有失效场景。脚本类机制在语义问题上失效。模型类机制在长上下文里 attention 漂。机制失效不是设计缺陷，是机制类型的固有属性。

要判断机制组合能不能覆盖两个地点，必须知道每个机制的失效边界。A 机制在某个场景失效，B 机制在这个场景不失效，A 的漏被 B 补上。这就是失效互补。互补分析的前提是失效边界能陈述。

失效边界陈述不清的机制无法进入互补组合。它承担的责任落在模糊的范围里，可信度就是零。5.3 的三层机制设计里，每一层的失效边界都要能陈述。

### 与 ch4 的引用点

- 载体自足性带来的冗余：段 3。这里引用 ch4 的结论，不重复论证
- 载体共同产出中的一致性检查：段 4。承接 ch4 但指出该检查会漏，所以载体块之间还是可能漂

### 写作陷阱

- 段 2、段 3 的漂移形态举例要具体到看得见的偏离，避免抽象讨论
- 段 4 的"两个地点覆盖所有漂移"是关键 claim。要立住，不要展开成防御性论证（"为什么不是三个""为什么不是一个"）
- 段 5 讲失效互补要克制。核心信息一次说完，避免反复申明

## 5.3 三层机制的分工

### Section takeaway

三层机制对应两个漂移地点。硬门禁和软门禁针对代码与载体块之间的漂移，按机制性质拆分。集成验证针对载体块之间的漂移。硬门禁失效于语义，软门禁失效于跨块，集成验证失效于块内诊断细节。三层的失效边界两两互补。

### 段落

**段 1：第一地点按机制性质拆两层**

Takeaway：代码与载体块之间的漂移分结构性和语义性两类。两类需要不同性质的机制。

结构性漂移的例子。字段类型对不上契约、函数签名跟载体规定的不符、错误码不在允许集合里。这类漂移不需要理解意思，看形状就能判断。

语义性漂移的例子。签名类型对但业务逻辑错。排序规则按相关度写成了按时间。错误处理策略写反。这类漂移看形状对，理解意思才知道错。

结构性用脚本判断最合适。语义性只能用模型判断。两类漂移都在同一个地点（代码与载体块之间），机制类型不同。

**段 2：硬门禁——脚本类机制**

Takeaway：硬门禁抓结构性漂移。失效边界在语义。

脚本的判断是确定性的。它不受 attention 影响，for 循环遍历一次结果稳定。载体里规定的 checklist 有 200 项，脚本能可靠地逐项检查是否都在。载体规定 schema 字段类型是 uuid，脚本能可靠地判断代码里的字段类型对不对。

硬门禁能落地的前提是载体本身机器可读。载体如果是散文写的，脚本没有可靠的规则去 parse。载体里的字段、层级、引用关系都要有明确格式。这样脚本才能起作用。

硬门禁的失效边界在语义。字段类型对了、命名对了，但字段的语义用途错了，脚本判断不出来。要抓语义漂移，需要下一层。

**段 3：软门禁——模型类机制**

Takeaway：软门禁抓语义性漂移。失效边界在跨块，源于 attention 承载力。

模型能理解语义。给它一段载体块的意图和对应代码，它能判断代码是不是忠实。这是脚本做不到的。

模型有 attention 承载力约束。让一个模型同时读几十页 spec 和几千行代码，做整体语义判断，它会跳读、漏东西。这跟 ch4 讲的载体分块是同一个物理约束。

在验证侧的解法是并行 subagent。每个 subagent 只审一个角度、独立 context 跑。一个 subagent 审"错误处理是否对齐载体"。另一个审"性能约束是否满足"。第三个审"接口契约的字段语义是否忠实"。每个 subagent 的 attention 集中在自己的角度上，避免了单模型审全部的漂。

胥克谦的一个原则要单独提。"只审不改。边审边改的不能并行。"改的动作干扰审的独立性。审出报告，报告再进入下一步决策，改由另一个环节做。

软门禁的失效边界在跨块。每个 subagent 的 attention 是块内的，它拿的是一个块的载体和一段代码。跨块的漂它抓不到。抓跨块需要另一层。

**段 4：集成验证——第二地点的机制**

Takeaway：集成验证抓载体块之间的漂移。用 API 契约加泳道加 Mock 预演跨块行为。

载体块之间的漂到代码侧的表现是集成失败。前端代码基于载体里的假设产出，后端代码基于载体里另一个（可能不同的）假设产出，两边合起来跑不通。

集成验证在合并之前预演跨块行为。前后端各在自己的泳道里跑。前端泳道里后端用 Mock 替代，Mock 遵守 API 契约的规定。反过来也一样。两边独立跑通自己的测试。然后跑真实集成，前端连到后端。跨块假设的差异在这时候暴露。

抓到之后回到载体分析。是载体本身的两块假设不一致（第二地点漂），还是一块载体清楚而另一块代码没对齐（第一地点漂但落到跨块表现）。前者补载体，后者补代码。

集成验证的失效边界在块内诊断细节。它能发现"合不上"，抓不到"是前端问题还是后端问题还是契约本身漏了"。诊断需要回到硬门禁和软门禁的结果。

**段 5：三层的互补关系**

Takeaway：三层的失效边界两两不重叠，加起来覆盖两个漂移地点。

硬门禁的语义盲区被软门禁覆盖。软门禁的跨块盲区被集成验证覆盖。集成验证的诊断盲区被硬门禁和软门禁的结果覆盖。

三层加起来在两个漂移地点上都有专门机制。第一地点的结构性漂由硬门禁抓，语义性漂由软门禁抓。第二地点的漂由集成验证抓。覆盖成立。

### 素材归属

- 硬软门禁双闸和结构化输出前提：段 2、段 3（胥克谦"两层门禁，一层模型语义门禁，一层代码硬门禁"、"要保证机器可读性"）
- 并行 subagent 独立 context：段 3（胥克谦访谈里的原话）
- "只审不改"原则：段 3（胥克谦原话，作为独立要点强调）
- API 契约加泳道加 Mock：段 4（胥克谦泳道分离原话）
- Attention 承载力回扣 ch4：段 3。不重复解释，只引用结论

### 与 ch4 的引用点

- Ch4 的 attention 承载力原则在段 3 再次应用。软门禁的 subagent 就是 attention 约束在验证侧的体现
- Ch4 的载体自足性和一致性检查在段 4 提到。集成验证是这条链条上的最后一道防线

### 写作陷阱

- 三层不要写成三个平行原则。它们是两个漂移地点加机制性质的展开
- Attention 承载力回扣 ch4 要克制。一句话引用，不重复机制解释
- "只审不改"要作为独立要点，不要淹没在段落中间
- 段 5 的互补关系一次说清，不要开头结尾各说一次

## 5.4 从载体到通过验证

### Section takeaway

用 ch4 建立的博客审核队列的载体走完整流程。前半段展示三层机制怎么从载体派生加人判定失效边界建起来。后半段展示建成的机制跑一遍五份产出，抓到三种漂移。整个流程沿用 4.3 的共同产出框架，元原则相同。ch5 特有的两点在于载体已在手让大模型能自动派生大部分候选检查项，以及人的判定内容从意图变成失效边界。人的介入只在两处：建立时判定失效边界，运行时载体出漏项要补决策。

### 段落

**段 1：起点——载体在手，大模型从载体派生候选检查项**

Takeaway：载体从 ch4 收敛出来。大模型从载体反推出三层的候选检查项。这一步不需要人介入。

Ch4 结尾产出的载体分五块：产品交互块、API 契约块、schema 块、通知机制块、垃圾处理块。每块自足，跨块契约在 API 契约块里明确。这份载体就是 5.4 的起点。

建立三层机制沿用 4.3 的共同产出框架，同一个元原则。差别在于载体已经在手。大模型能直接从载体反推候选检查项，不需要人先告诉它检查什么。

派生的具体路径。载体里的 schema 字段类型规定推硬门禁的字段检查，比如 reviewer_id 是 uuid 就派生"检查 SQL 字段类型是 uuid"这个脚本检查项。载体里的每一条意图条目推软门禁的 subagent 任务，比如"合并通知要分类列出通过和拒稿"派生一个"审通知模板文案是否分类"的 subagent。载体里的跨块契约推集成验证的 API Mock 设置，比如"session 用 token 表示"派生一个 Mock 设置来模拟 token 交互。

三层机制的初稿基本由大模型自动铺开。人的介入位置向后收。

**段 2：人判定失效边界**

Takeaway：候选检查项摆出来之后，人的介入在失效边界。判定沿用 4.3 三条件，判定内容是失效边界。

大模型能派生候选检查项，不知道哪些 critical、哪些是同类冗余、这一层的能力上限画在哪、允许哪些漂逃过。这些是人判断的。判断依然遵守 4.3 三条件（领域、杠杆、呈现形式），只是判定内容从意图变成失效边界。

三个博客案例的判定 walkthrough。

例 1，硬门禁的 uuid 类型检查。抛回给技术 lead，领域够。杠杆够，字段类型错就是数据完整性问题。呈现用"字段类型强校验，允许还是不允许类型隐式转换"。判定："不允许，严格校验"。写入硬门禁失效边界文档："抓所有字段类型不匹配，不抓 uuid 的语义误用，比如用户 uuid 被用作会话 uuid 这类误用"。

例 2，软门禁的拒稿反馈 subagent。抛回给产品经理，领域够。杠杆够，反馈机制决定用户体验。呈现用"允许分类标签之外的自由文字备注共存吗"。判定："允许，备注是补充说明"。写入软门禁失效边界文档："抓分类标签是否作为主要机制，允许分类标签加备注共存，可能对分类标签为空但备注独立填写的情况误报"。

例 3，集成验证的 session token 传输。抛回给架构师，领域够。杠杆够，安全性关键。呈现用"session token 用什么方式传输"。判定："cookie，团队现有前端库都是 cookie based"。写入集成验证失效边界文档："抓 token 传输方式不匹配，不抓 token 内容的语义正确性，那部分是块内的软门禁范围"。

三个判定内容都在 4.3 三条件的判定框架内。判定的是失效边界不是意图，但接口原则相同。

**段 3：失效边界文档做覆盖检查**

Takeaway：三层的失效边界文档合起来做覆盖检查。覆盖成立三层机制才建立完成。

三份文档说清楚每层的能力和限制。硬门禁抓所有结构性违规，不抓语义误用。软门禁抓块内语义漂移，不抓跨块假设，可能对同类冗余误报。集成验证抓跨块契约差异，不抓块内诊断细节。

三份文档一比对做覆盖检查。问两个问题。有没有漂移地点被两层都声称能抓、但两层机制类型相同、实际是同类冗余？有没有漂移地点没被任何一层覆盖？前者是浪费，后者是漏洞。任何一个成立都要回循环补文档或补机制。

博客案例这一版覆盖检查通过。第一地点的结构性漂由硬门禁抓，语义性漂由软门禁抓。第二地点的漂由集成验证抓。两个地点都有专门机制。三层机制的初始建立完成，可以跑了。

**段 4：跑一遍——硬门禁扫结构**

Takeaway：五个 Agent 产出代码。硬门禁先跑，抓结构性漂移。

五个 Agent 从五个块各自产出代码。前端 Agent 拿产品交互块，产出前端代码。后端 Agent 拿 API 契约块，产出后端代码。数据库 Agent 拿 schema 块，产出建表 SQL 和迁移脚本。通知 Agent 拿通知机制块，产出事件到发送通道。反垃圾 Agent 拿垃圾处理块，产出识别到隔离流程。

硬门禁先跑。检查项包括载体 checklist 覆盖度、schema 字段类型匹配度、API 签名一致性、错误码规范、命名规范。

在这份产出上抓到两个问题。数据库 Agent 的 SQL 里 reviewer_id 字段类型写成了 int，schema 块规定的是 uuid。后端 Agent 有两个端点的错误响应漏了 error_code 字段，API 契约块规定所有错误响应必须带这个字段。

问题回给对应 Agent 改，脚本再扫，通过。

硬门禁的失效边界在这里也能看到。通知块的合并模板文案是散文，脚本判断不了文案的意思对不对。语义要下一层抓。

**段 5：软门禁并行审语义**

Takeaway：多个 subagent 独立 context 各审一个角度。汇总标出块内语义漂移。

启动多个 subagent，每个只审一个角度、独立 context 跑。

Subagent A 审通知块。载体规定合并通知要分类列出通过和拒稿。它检查实际文案，发现写的是"你的三篇稿件都被审核通过"，把通过和拒稿混在一起。语义漂。

Subagent B 审反垃圾块。载体规定识别到疑似垃圾先隔离等主编确认。它检查"主编确认"动作有没有独立入口，找到了，对齐。

Subagent C 审 schema 块。载体规定审核历史保留三年。它检查 SQL 里的分区归档策略，按年分区加冷存储归档都到位，对齐。

胥克谦的一条原则要单独提。"只审不改。边审边改的不能并行。"改的动作干扰审的独立性。审出报告，报告再进入下一步决策，改由另一个环节做。

主流程汇总报告。通知块的语义漂抛回通知 Agent 修改。修改后再走软门禁到通过。

软门禁的失效在这里也能看到。每个 subagent 只看一个块，两个块之间的漂它抓不到。跨块要下一层。

**段 6：集成验证跑跨块契约**

Takeaway：API 契约加泳道加 Mock 预演跨块行为。抓块间假设差异。

前端在自己的泳道跑，后端用 Mock 替代，Mock 遵守 API 契约。反过来也一样。两边独立通过。

跑真实集成。前端连到后端，走一个完整用户旅程。作者投稿，主编审核，通过或拒稿，作者收到通知。

集成挂了。前端发的请求带的是 Cookie: session=xyz。后端读的是 Authorization header，找不到 token，返回 401。

回到载体分析。API 契约块规定"session 用 token 表示"，前端和后端都遵守了这条。契约没规定 token 用什么方式传输。这是载体本身的漏项，第二漂移地点。

解决方式回到共同产出流程，抛回可判定决策（对应段 2 里例 3 的建立时判定，运行时载体漏项也走同一个流程）。产品经理选 cookie，理由是团队现有前端库都是 cookie based。载体补决策。前后端 Agent 都基于新载体修改代码。再跑集成，通过。

集成验证的失效在这里也能看到。它发现"合不上"但不告诉你是前端错了还是后端错了还是契约漏了。诊断要靠回到载体分析。

**段 7：三层互补落到具体产出上**

Takeaway：每一层各抓自己那类漂移。互补关系在这个走通里可见。

硬门禁抓的是代码结构不符合载体，uuid 类型和 error_code 字段这两个。第一漂移地点的结构性漂。

软门禁抓的是代码语义不符合载体，通知合并文案错位。第一漂移地点的语义性漂。

集成验证抓的是载体本身有漏，API 契约没规定 token 传输方式。第二漂移地点漂。

三层各自的失效场景在例子里都能观察到。硬门禁抓不到文案语义，语义靠软门禁补。软门禁抓不到跨块假设，跨块靠集成验证补。集成验证抓不到块内诊断细节，诊断要回到硬软门禁的结果。三层的失效不重叠。加起来覆盖两个漂移地点。

**段 8：正常流里人不进入**

Takeaway：三层跑完产出合并。人只在两处介入，都是共同产出的一部分。

三层验证过程里的所有代码修改由 Agent 自动执行。硬门禁标问题，Agent 修，脚本再扫。软门禁 subagent 出报告，主流程根据报告让 Agent 修，再审。集成验证发现载体漏，补决策后 Agent 修，再跑集成。

人可能进入的位置只有两个。第一是建立机制时判定失效边界（段 2 的三个例子）。第二是运行时载体出漏项要补决策（段 6 的 session 传输方式）。两处都符合 4.3 的共同产出框架，只是介入点在整个链条里的位置不同。运行时的补决策跟建立时的判定共用一个机制。

正常运行流里人不介入。三层通过，产出合并。五份产出合起来是完整的博客审核队列。

跟卷一相比形态不变，可信度的来源变了。卷一里的最后一道是人。卷二里的最后一道是失效互补的三层机制。产品会变，模型会升级，新场景会暴露旧机制的漏。载体和验证机制本身怎么持续维护是下一章的话题。
