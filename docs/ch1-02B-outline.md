# 02B Outline：用结构传达意图

> 状态：detailed outline
> 日期：2026-04-07

## Section Takeaway

信息天然有层级，每一层的抽象程度、演进速度、适用范围不同。Context 有限意味着你不能把所有层都塞给 Agent，你必须选择加载哪几层。在每一层内，你需要从三个维度（意图、验收、约束）表达清楚，其中验收维度的核心作用是检测这一层跟上一层的对齐有没有丢失。

---

## 一、从对话到文档

**段落 1：文档解决载体问题**
- Takeaway：文档解决了 02A 诊断的三个对话缺陷（注意力衰减、指令冲突、compaction）
- 文档可以原地修改，不留矛盾记录。文档独立于对话，不跟聊天内容争抢 context。文档持久化在文件系统里，compaction 删不掉它。
- 展开每个点用一两句话说清机制，不需要重复 02A 的例子

**段落 2：文档驱动的效果和局限**
- Takeaway：文档驱动已经是巨大进步，但自然语言文档还有歧义问题
- 很多开发者从纯对话切到维护一份 spec 文档后，产出质量立刻提升。方向是对的。但自然语言文档带来一个新问题：你写的和 Agent 理解的可能不是一回事，而且你发现不了这种差异，直到看到代码。
- 这个局限引出下面的问题：文档该怎么写，才能最大程度消除歧义？

> 过渡：解决歧义的答案不是"写更多"，而是"写对结构"。要理解什么结构是对的，先要理解信息本身的性质。

## 二、信息的自然分层

这是 02B 的核心 principle。

**段落 1：人类团队的类比**
- Takeaway：人类程序员能协作，不是因为他们共享所有信息，而是因为他们共享了正确层级的信息
- 一个团队里，程序员 A 不知道程序员 B 用了什么字段名、什么排序算法、什么变量命名。但他们写出来的代码能合在一起工作。为什么？因为他们共享了足够高层的 context：产品要解决什么问题，系统的架构是什么，模块之间的接口怎么定义的。他们不需要共享低层细节，因为高层的共识已经足够约束低层的决策方向。
- 如果高层共识缺失，两个程序员即使各自的代码都写得很好，合在一起也会出问题：重复实现相同功能、接口不兼容、数据模型冲突。

**段落 2：信息层级的三个属性**
- Takeaway：不同层级的信息在抽象程度、演进速度、适用范围上有本质差异
- 用一个具体产品（比如一个博客系统）做例子，从上到下走一遍：
  - Vision："让非技术用户也能轻松发布和管理内容"。抽象、极少变、整个产品团队都需要知道。
  - 架构决策："前后端分离，API 用 REST，数据库用 PostgreSQL"。中等抽象、偶尔变（比如从 REST 迁到 GraphQL）、所有开发者需要知道。
  - Feature spec："文章搜索功能支持关键词全文搜索，结果按相关度排序"。具体、随迭代频繁变化、只有做这个 feature 的人需要知道。
  - Task 细节："在 search.ts 里调用 PostgreSQL 的 tsvector 全文搜索，结果返回前 20 条"。非常具体、随实现决策变化、只在执行这个 task 时需要。
- 从上到下：越来越具体，变得越来越快，需要知道的人（或 Agent）越来越少。

**段落 3：这跟 Agent 的 context 限制直接相关**
- Takeaway：因为 context 有限，你不能把所有层都装进去。你必须选择：当前任务需要哪几层。
- 如果你把 vision、架构、所有 feature spec、所有 task 细节全部塞进 context，大部分信息对当前任务是噪声，会稀释 Agent 对真正相关信息的注意力。
- 正确的做法：始终加载高层（vision、架构，因为它们稳定且广泛适用），按需加载低层（当前 feature 的 spec 和相关 task）。这就是为什么你需要把信息结构化地拆分到不同的文档里，而不是写成一个大文件。
- Ryan 的实践：project-context.md 承载高层信息（技术栈、架构、模块索引），限制 200 行。每个 feature 有自己的 spec/task/checklist 三份文档，只在执行该 feature 时加载。CLAUDE.md 承载跨层的强制约束。三类文档对应不同的层级和不同的加载策略。

**段落 4：分层原则的实践含义**
- Takeaway：判断一条信息该放在哪一层，看它的变化频率和适用范围
- 如果一条信息在整个项目生命周期内基本不变，所有任务都需要它，它属于高层，应该放在持久加载的项目上下文里。
- 如果一条信息只跟某个 feature 相关，feature 完成后可能就过时了，它属于任务层，应该放在那个 feature 的 spec 里。
- 如果你发现自己在每个 feature 的 spec 里都重复写同样的信息（比如"我们用 REST API"），说明这条信息应该上提到项目上下文层。
- 如果你的项目上下文膨胀到上千行，说明你把太多低层信息塞进了高层文档，需要下沉。

## 三、每一层的三个维度

**段落 1：引出维度的概念**
- Takeaway：不管在哪一层，你都需要回答三类问题：意图、验收、约束
- 上一节讲了信息为什么要分层（不同层的性质不同，context 有限）。这一节讲每一层里面该有什么内容。
- 不同的 spec 框架模板差异很大（BMAD 十几个字段，OpenSpec 很精简），但它们在每一层都在要求回答同样三类问题。

**段落 2：意图维度（这一层的目的是什么）**
- Takeaway：意图维度定义了"做什么"和"为什么做"，它的具体内容在每一层都不同
- Vision 层的意图：产品要解决什么问题，为谁解决。
- 架构层的意图：系统为什么这样组织（比如为什么前后端分离，为什么选 PostgreSQL）。
- Feature 层的意图：这个功能为谁解决什么问题。通常用用户故事表达。"作为博客作者，我希望能通过关键词搜索已发布的文章，这样我可以快速找到之前写过的内容。"这句话包含了谁、要什么、为什么三个信息。
- 展开讲 feature 层的用户故事为什么有效：它天然具有可验证性，"用户能搜索文章吗？"有 yes/no 答案。（这个特性在 02C 讲分解时会变得很重要。）

**段落 3-4：验收维度（怎么知道这一层是对的）**
- Takeaway：验收维度的核心作用是检测当前层跟上一层的对齐是否丢失
- 这是三个维度中最关键的。验收不只是"测试通过了没有"。它在每一层检查的是一个更根本的问题：这一层的内容是否忠实地实现了上一层的意图。
  - Vision 层的验收：用户故事和用户旅程能否反映 vision？如果 vision 说"让非技术用户轻松发布内容"，但用户旅程里要求用户手动配置 Markdown 渲染引擎，说明旅程跟 vision 有偏差。
  - 架构层的验收：PRD 的每个需求能否对应回用户旅程？如果某个需求找不到它服务的用户旅程，要么需求是多余的，要么旅程有遗漏。
  - Feature 层的验收：Gherkin 场景。Given/When/Then 格式的具体场景描述。验证这个 feature 的行为是否跟 spec 的意图一致。
  - Task 层的验收：测试通过。代码行为是否跟 task 描述一致。
- 展开 feature 层的 Gherkin 场景（这是读者最需要的层）：
  - 例子：Given 数据库中有一篇标题包含"性能优化"的文章，When 用户在搜索框输入"性能"并点击搜索，Then 搜索结果中显示这篇文章并高亮匹配关键词。
  - 一个功能通常需要覆盖正常路径、边界情况（搜索词为空）、异常情况（没有匹配结果）。
  - 没有验收标准时你和 Agent 对"完成"的定义可能完全不同。Agent 觉得搜索实现了（能搜、有结果），你觉得没完成（没高亮、没分页、没处理空结果）。验收场景把这种隐含的期望差异提前暴露出来。
  - Ryan 的经验："一个 user story 加几个场景描述，就已经能判断出 AI 跟我的理解了。"

**段落 5：约束维度（这一层的边界在哪）**
- Takeaway：约束维度防止在"做什么"之外的地方制造破坏
- 每一层都有约束：
  - Vision 层：市场约束、合规要求、商业模型限制
  - 架构层：技术能力边界、性能要求、已有系统的兼容性
  - Feature 层：这次改动的边界在哪，不能碰哪些模块，有什么可以复用
  - Task 层：改动的文件范围、编码规范
- Feature 层展开：你让 Agent 加搜索功能，它可能顺手改了文章列表的排序逻辑。技术上可能合理，但不在你的预期内，可能破坏已有用户的使用习惯。约束维度明确告诉 Agent：改动的边界在哪。
- Ryan 的 spec 里有 Context Analysis 字段（参考代码、相关文档、历史 feature），有效防止 Agent 重复造轮子。
- 空字段的代价：Ryan 观察到 spec 里技术方案字段为空时，编码 Agent 会自己编造方案出现幻觉。空字段意味着那个维度的对齐没有发生。

## 四、分解过程中的漂移与交叉验证

这一节是验收维度的延伸。验收维度说"每一层要检查跟上一层的对齐"。但在实践中，你从一个层生成下一个层（从 spec 拆出 task，从 task 推出 checklist），每一步都在创造新的信息。生成新信息的过程本身就可能引入漂移。这一节讲为什么会漂移，以及怎么用交叉验证来检测。

**段落 1：为什么生成新层级的信息会引入漂移**
- Takeaway：漂移有两个来源，一个是 Agent 主动加入自己的理解，一个是 context 压力导致它被动遗漏上层约束。两者的结果一样：下层信息跟上层意图不一致。
- 主动偏移：你有一份 feature spec，让 Agent 从中生成 task list。这个过程是 Agent 在"翻译"你的意图：从"用户能搜索文章"翻译成"在 search.ts 里加一个 buildQuery 函数"。翻译的过程中 Agent 加入了自己的理解和决策。这些决策可能跟你的意图一致，也可能偏了。
- 被动遗漏：Agent 在生成 task list 的时候，context 里已经有了 project context、feature spec、对话历史等大量信息。某些 spec 里的约束可能因为注意力分配不足被忽略了。这跟 02A 讲的注意力衰减是同一个机制，只是这次发生在层级生成的过程中。
- 两种漂移的后果一样，而且会逐层叠加：spec 到 task 偏一点，task 到代码又偏一点。所以验收不是在最后做一次就够了，每次生成新层级的信息都需要检查跟上层的一致性。

**段落 2：交叉验证作为漂移检测的方法**
- Takeaway：让 Agent 从不同角度看同一份意图，多次产出之间的矛盾就是漂移的信号
- 具体做法（Ryan 的三次思考）：
  1. 从需求生成实现方案和影响分析（spec）。这是 Agent 第一次理解需求。
  2. 从方案拆成执行步骤（task list）。这是第二次理解。如果某个步骤写不清楚，说明方案在那里还不够具体。
  3. 从步骤反推验收标准（checklist）。这是第三次理解。从"怎么做"反推"怎么算对"。
- 为什么这能检测漂移：如果 checklist 里出现了 spec 没提到的检查项，说明 task 拆分过程中引入了 spec 没有覆盖的内容（可能是合理的补充，也可能是 Agent 自己加戏了）。如果某个 checklist 项跟 spec 矛盾，说明意图在某个环节发生了偏移。三份文档之间的一致性是对齐的证据，矛盾是漂移的信号。
- Ryan 把第三轮称为"对抗性测试"，因为它从一个完全不同的角度（验收而非实现）重新审视了前两轮的产出。

**段落 3：这个原则的一般化**
- Takeaway：交叉验证不只适用于 spec/task/checklist 这个具体的三文档体系，它是一个通用原则
- 核心思想是：当你从一个层级的信息生成下一个层级时，用第三个角度来检查两者是否一致。具体形式可以不同：可以是三文档体系，可以是让另一个 Agent review，可以是自动化的一致性检查工具（比如 Spec Kit 的 analyze 命令做的就是只读的跨文档一致性分析）。
- 形式不重要，重要的是意识到：每次生成新层级的信息都有漂移风险，你需要一个机制来检测它。

## 五、"写更长的 prompt"为什么不管用

**段落 1**
- Takeaway：歧义的根源不是信息量不够，而是关键维度的问题没有被回答
- 你可以把搜索需求写成三页自然语言描述，详细说明搜索框的位置、颜色、字体。但如果你没回答"空结果怎么办""搜索范围是什么""触发方式是什么"，三页描述跟一句话的 prompt 一样有歧义。区别只是歧义藏在更多文字里更难发现。
- 结构化的维度把你必须回答的问题摆在面前，让你无法跳过。
- Spec Kit 的 clarify 工作流做了一个有意思的设计：它用 10 个类别的结构化问题主动检测 spec 里的歧义（功能范围、领域模型、交互设计、非功能性、集成、边界情况、约束、术语、完成信号、占位符），每次最多问 5 个问题。这些问题问的是写 spec 的人，帮你发现自己还没想清楚的地方。

## 过渡到 02C

到这里你有了完整的方法论框架：信息分层管理（高层持久加载，任务层按需加载），每一层用三个维度表达清楚（意图、验收、约束），层与层之间用交叉验证检测漂移。
